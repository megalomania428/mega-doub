# mega-doub

Backup utility written in Go.

## Build

Building and testing need the module `duplicacy.invalid/v3` from a file-based Go module proxy in a release archive, so `GOPROXY` and `GONOSUMDB` must be set for it; `duplicacy.invalid` must not be in `GOPRIVATE` or `GONOPROXY`, as Go would then fetch it directly and fail. The script `scripts/module-proxy.sh` downloads and unpacks the archive into `${RUNNER_TEMP:-/tmp}/mega-doub-modules` once, a later run reuses it, and prints both variables as `NAME=value` lines; the integrity of the module is checked by `golang/go.sum`; a proxy that lost the archive of the module is downloaded again. The script needs `curl`, `tar` with `xz` support and GNU `mktemp`, `mv` and `flock`, and refuses a `RUNNER_TEMP` that is not an absolute path of ASCII letters, digits, `/`, `.`, `_` and `-`; `RUNNER_TEMP` also moves the directory elsewhere, such as on a host where another user owns `/tmp/mega-doub-modules`.

```bash
proxy="$(scripts/module-proxy.sh)" && export ${proxy}
cd golang
version="$(git describe --tags --always --dirty)"
commit="$(git rev-parse --short HEAD)"
go build -o mega-doub -ldflags "-X main.version=${version} -X main.commit=${commit}" \
  ./cmd/mega-doub
```

The workflow `.github/workflows/build.yaml` runs the checks and the build through scripts that work from any directory and leave nothing in the working copy: the binaries, the archives and the files of the smoke checks go into `${RUNNER_TEMP:-/tmp}`, where [scripts/build.sh](scripts/build.sh) removes and recreates its directories `mega-doub-build` and `mega-doub-out` on every run; `RUNNER_TEMP` moves them elsewhere, such as on a host where another user owns them in `/tmp`. [scripts/tests/go-checks.sh](scripts/tests/go-checks.sh) runs `go mod verify`, `gofmt -l`, `go build`, `go vet` and `go test -race` in `golang/`, `scripts/build.sh` builds the binaries of all supported platforms with `CGO_ENABLED=0` into `mega-doub-build/<os>-<arch>/mega-doub` and packs them into `mega-doub-out/`, and [scripts/tests/go-smoke.sh](scripts/tests/go-smoke.sh) `<binary>` checks the exit codes of a built binary. `scripts/tests/go-checks.sh` and `scripts/build.sh` need the variables of `scripts/module-proxy.sh` in the environment; `scripts/build.sh` also needs bash 4.1 or newer (the redirection `exec {lock}>` does not parse in bash 3.2 of macOS), `scripts/tests/go-smoke.sh` needs bash 4.0 or newer (`mapfile` and `${name,,}` are missing in bash 3.2 of macOS), Go of the version in `golang/go.mod`, `git`, `file`, `flock` and GNU `tar` with `xz` support (the options `--owner`, `--group`, `--numeric-owner` and `--mode`), and `go test -race` needs cgo with a C compiler. `scripts/build.sh` waits for another run of itself with the same `${RUNNER_TEMP:-/tmp}`, so concurrent builds that run the smoke check of the built binary need a `RUNNER_TEMP` each, and both `scripts/build.sh` and `scripts/tests/go-smoke.sh` refuse a `RUNNER_TEMP` that is not an absolute path.

```bash
proxy="$(scripts/module-proxy.sh)" && export ${proxy}
scripts/tests/go-checks.sh
scripts/build.sh
scripts/tests/go-smoke.sh "${RUNNER_TEMP:-/tmp}/mega-doub-build/linux-amd64/mega-doub"
```

### Releases

A pushed tag `v*` builds the release of the tag with the archives of all platforms and publishes it with the generated release notes. A pull request from this repository builds the one shared draft release `v999` instead: the archives of every build are added to it and replace the ones with the same name, the older ones stay, so the draft is cleaned up by deleting it by hand. `v999` must stay a draft: the pull requests do not touch a published release, but they do update a published prerelease `v999` and replace its archives. Pull requests from forks and from Dependabot run the checks, the build and the smoke checks without publishing anything. An archive `mega-doub-<version>-<os>-<arch>.tar.xz` holds the only file `mega-doub`, and its version has `.` and `/` replaced with `_`: the tag, such as `mega-doub-v0_0_1-linux-amd64.tar.xz`, or outside a tag `git describe` with `.dev.<run number>.<run attempt>` of GitHub Actions, such as `mega-doub-v0_0_1-3-g1a2b3c4_dev_42_1-linux-amd64.tar.xz`, where each number is `0` outside GitHub Actions. `mega-doub version` prints the same version with `.` and `/` kept.

- to release a version, tag `master` and push the tag:

  ```bash
  git checkout master && git pull; TAG4REL='v0.0.1'
  git tag -fm $(git branch --sho) ${TAG4REL} && git push --force origin ${TAG4REL}
  ```

## Usage

```text
mega-doub [global flags] <command> [flags]
```

Commands:

- `init` – initialize the storage, see [Storage](#storage);
- `backup` – back up the copy directory `global.copy_dir` to the storage and then prune the storage when `prune.enabled` is set, see [Storage](#storage);
- `prune` – prune old revisions in the storage by `prune.keep`, see [Storage](#storage);
- `check [--files] [--chunks]` – check the storage integrity, optionally every file or every chunk;
- `verify [--revision N] [--bytes SIZE]` – verify a revision by a test restore: revision `0` is the latest one, `SIZE` is a number with an optional `K`, `M`, `G` or `T` suffix;
- `list [--revision N]` – list revisions in the storage, revision `0` lists all of them;
- `config validate [--resolve]` – validate the configuration file, with `--resolve` also resolve the secrets, see [Secrets](#secrets);
- `config show` – print the effective configuration of the file, without the overrides of `global.retry` from the environment, with the secrets masked, see [Output](#output);
- `version` – print `mega-doub <version> (<commit>)`, same as `--version` given without a command;
- `help [command]` – print help, same as `--help` and `-h`.

Global flags are accepted before and after the command name:

- `--config`, `-c` – configuration file, `/usr/local/etc/mega-doub/main.yaml` by default;
- `--log-level` – `debug`, `info`, `warn` or `error`, `info` by default;
- `--log-format` – `text` or `json`, `text` by default;
- `--no-progress` – draw no progress bar, whatever `global.progress` holds;
- `--dry-run` – plan the run without changes; for now `init`, `backup`, `prune`, `check`, `verify` and `list` only resolve the secrets, log their invocation and print the configuration, see [Output](#output).

## Configuration

The configuration is one YAML document, `/usr/local/etc/mega-doub/main.yaml` by default or the file given with `--config`. The commented example [golang/testdata/example.yaml](golang/testdata/example.yaml) shows the layout, and [golang/testdata/example-vault.yaml](golang/testdata/example-vault.yaml) takes the secrets from Vault with `vault:` references.

- The file is at most 1048576 bytes; an empty file, a file of comments only and a `null` document are errors.
- Loading is strict: an unknown key at any level and a repeated key in one mapping are errors, also for keys that come from an alias or `<<`.
- Anchors, aliases and the merge key `<<` are allowed anywhere; nesting deeper than 64 levels and excessive alias expansion are errors. The `templates` section holds anchors: a template is checked only where it is used, an unused one is not checked.
- `<<` takes one alias or a list such as `<<: [*a, *b]`; two `<<` keys in one mapping are an error. A local key overrides the same key from `<<`, an earlier template of the list overrides a later one. A repeated template name in `templates` is not detected.
- A missing key and an explicit `null` select the default; an explicit `0`, `false` or `''` is kept. `global.copy_dir` and `global.state_dir` default to `/var/lib/mega-doub/copy/<instance>` and `/var/lib/mega-doub/state/<instance>`.
- Durations need a unit, such as `30s` or `12h`; only `0` is allowed without one. Sizes take an optional `K`, `M`, `G` or `T` suffix, a plain number is bytes.
- Booleans are `true`, `false`, `yes`, `no`, `on` and `off` in lower case, capitalized or in upper case, and `y`, `Y`, `n`, `N`; `1`, `0` and a quoted `'true'` are errors.
- `global.log_level` and `global.log_format` take the values of `--log-level` and `--log-format`; a flag given explicitly wins over the file.
- `global.progress` is the list of the elements of the progress bar of `backup`, in any order: `bytes` – the bytes done and the total, `elapsed` – the time since the start, `rate` – the speed, `bar` – the bar itself, `percent` – the share done and `eta` – the time left. The bar shows the elements in this order whatever the order of the list, the default is all six, and `prune` draws no bar. An empty list `[]` and `--no-progress` turn the bar off, and `--no-progress=false` does not turn on the bar of an empty list. A string, such as the former `auto`, `always` or `never`, is an error of loading that asks for a list, and an unknown or a repeated element is a problem of the validation at the element, such as `global.progress[1]`.
- `global.retry` defaults to the values of go-lib-ci: `max_retries_time: 111s`, `backoff_initial: 1s`, `backoff_step: 1s`, `backoff_step_attempts: 3` and `backoff_cap: 7s`; explicit values are kept as written. As in go-lib-ci, `max_retries_time: 0` selects the default, a negative value disables the retries and a positive one limits the total wait between the attempts of one request, the time of the attempts is not counted; a `backoff_*` value of `0` or below selects its default. The schedule applies to every request to Vault, see [Secrets](#secrets).
- The environment variables `MAX_RETRIES_TIME`, `BACKOFF_INITIAL`, `BACKOFF_STEP`, `BACKOFF_STEP_ATTEMPTS` and `BACKOFF_CAP` override `global.retry.max_retries_time`, `backoff_initial`, `backoff_step`, `backoff_step_attempts` and `backoff_cap`: the environment wins over the file, which wins over the default, and an empty variable counts as unset. They are read with every file that is read, `config show` included, and take a Go duration, such as `30s` or `-1s`, or an integer for `BACKOFF_STEP_ATTEMPTS`. The same rules apply: `MAX_RETRIES_TIME=0s` selects the default of go-lib-ci (111 seconds), a negative value disables the retries and a `BACKOFF_*` value of `0` or below selects its default.
- `global.timeout`, `12h` by default, limits a run of `init`, `backup` and `prune` from the end of the validation of the file: the resolution of the secrets and the work of the command count. When it runs out, the run stops as on a signal, logs `level=ERROR msg="timed out"` with the field `timeout`, the effective value such as `12h0m0s`, instead of `interrupted` and exits with `4`; a signal is logged as `interrupted` as before, and a signal that comes after the expiry adds that record. A signal or the timeout stops the wait between the attempts of a request to the storage at once and a backup or a prune at the next check of duplicacy, which may take a while; a request that comes while a backup uploads its revision at the end or while a prune changes the storage in its final step does not stop them: they complete, and the run still exits with `4`. The limit and a signal stop the work cooperatively, so a write of the output that nobody reads delays the exit until the write ends.

Every problem of the file is logged at once as a separate record `level=ERROR msg="invalid configuration"` with the fields `file` (absolute path), `line`, `column`, `path` and `error`, ordered by position with the problems without a position last in the order they are found, and the exit code is `2`. An environment variable of `global.retry` that does not parse is such a problem too: its `file` is `<env NAME>`, such as `file="<env MAX_RETRIES_TIME>"`, its `path` is the key it overrides, such as `global.retry.max_retries_time`, it has no position, and the file is not validated then. After the file loads, every variable of `global.retry` taken from the environment is logged before the records of the validation as `level=DEBUG msg="retry option from environment"` with the fields `variable` and `value`, the value as written. The path names the key where it is used, with list indexes, such as `targets[1].sources[0].port`, `prune.keep[2]` or `storage.keys.b2_id`; a key with characters other than ASCII letters, digits, `_` and `-` is quoted in brackets as a Go string, such as `storage.keys["a.b"]` or `storage.keys[""]` for an empty one. The position is where the key or the value is written: a key or a value that comes from a template through `<<` and a value given by an alias are reported at their line in the template or at the anchor, once for every place that uses them, or once without a path when the path is not known, while an alias written as a key is reported where it is written. A field without a value is left out: a problem without a known position has no `line` and `column`, a problem whose path is not certain, such as a value of an alias used by fields of different types, has no `path`. `mega-doub config validate` checks the file and, when it has no problems and with `--resolve` all its secrets resolve, logs `level=INFO msg="configuration is valid"` with the absolute path in the field `config`; the `command` record of the other commands carries the same path.

A file that loads is validated next, a file that fails to load is not. The problems of the validation are logged all at once in the same way and give the exit code `2`; a problem of a field is reported at its value, an explicit `null` included, or at the key of the nearest present ancestor when the field is missing; a problem of `global.retry` that a value from the environment causes has the `file` `<env NAME>` of the variable and no position. Warnings are logged before the problems as `level=WARN msg="configuration warning"` with the same fields and `warning` instead of `error`, they do not change the exit code. The rules:

- `global.instance` matches `^[A-Za-z0-9_-]+$`, `global.parallel_targets` and `global.parallel_sources` are at least `1`, every element of `global.progress` is one of `bytes`, `elapsed`, `rate`, `bar`, `percent` and `eta` and is not repeated, `global.timeout` is above zero; an empty string is checked like any other value.
- `global.copy_dir` and `global.state_dir` are absolute paths that are neither equal nor inside each other. They are compared as written after cleaning, without resolving links and with letter case: `/a/copy` and `/a/copy2` pass, while `copy_dir: /` holds any `state_dir`. A local storage, the path of a valid `storage.url` that is an absolute path or follows `flat://` or `samba://`, is compared the same way with each of the two directories that is an absolute path: it is neither equal to it, nor inside it, nor holds it, since a backup would put the storage or the state of the run into the archive. Every such directory gives its own problem at `storage.url`, the copy directory first: `must differ from global.copy_dir`, `must not be inside global.copy_dir` or `must not hold global.copy_dir`, and the same with `global.state_dir`; a storage URL of another form is not compared.
- `global.retry`, with the overrides from the environment applied: the effective `backoff_cap`, after the defaults replace the values of `0` and below, is not less than the effective `backoff_initial`, and `(backoff_cap / backoff_step + 1) * backoff_step_attempts` of the effective values with integer division fits a signed 64-bit integer; there are no other limits.
- An empty string in a required field is reported as `required` only, without the checks of its format; an empty string in an optional field, such as `vault.address` or `vault.ca_file`, means it is not set.
- `vault.address` and `vault.token` are required when a secret reference starts with `vault:`, except `vault.token` itself and the fields that a local target does not allow; a malformed `vault:` reference counts too. `vault.address`, when set, is an `http` or `https` URL with a host, an optional port from `1` to `65535`, an optional path `/` and without user information, query and fragment; only the first broken rule is reported, without the address. An `http` address gives the warning `vault token is sent in clear text`. `vault.token` is not a `vault:` reference, `vault.timeout` is above zero and `vault.ca_file`, when set, is an absolute path.
- `storage.name` is not empty and not `ssh` in any letter case. `storage.url` has a form that duplicacy creates a storage from: an absolute path, such as `/srv/backup`, or `flat://` or `samba://` followed by an absolute path, such as `flat:///srv/backup`, for a local storage that is not the root directory; or a URL `<type>://[<user>@]<host>[/<path>]` of the type `sftp`, `sftpc`, `s3`, `s3c`, `minio`, `minios`, `wasabi`, `dropbox`, `b2`, `b2-custom`, `azure`, `acd`, `gcs`, `gcd`, `one`, `odb`, `hubic`, `swift`, `webdav`, `webdav-http`, `fabric`, `storj` or `smb` in lower case, such as `b2://bucket/prefix` or `sftp://user@host/path`. `sftp` and `sftpc` need a path, `azure` a container, such as `azure://account/container`, `webdav`, `webdav-http` and `smb` a user, `smb` a share followed by `/`, such as `smb://user@host/share/` or `smb://user@host/share/path`, and `b2-custom` a bucket after the download host, such as `b2-custom://host/bucket`; the values of the host and the port are not checked, an empty host is a form error, and a path of `sftp` and `sftpc` is not made of slashes only. The user information has no password, an empty one included, and a colon in the user, such as the Swift name `tenant:user`, counts as a password and is rejected: the password of a user is a key of `storage.keys`, such as `ssh_password`. Only the first broken rule is reported, the URL is never logged. `storage.snapshot_id` matches `^[A-Za-z0-9_-]+$`, `storage.password` is required, `storage.threads` is at least `1`, and every key of `storage.keys` and its value are not empty.
- With a valid `storage.url`, `storage.keys` has only the keys of its type, named without the prefix of `storage.name`, and all the required ones: `b2` and `b2-custom` require `b2_id` and `b2_key`; `s3`, `s3c`, `minio` and `minios` – `s3_id` and `s3_secret`; `wasabi` – `wasabi_key` and `wasabi_secret`; `azure` – `azure_key`; `gcs` – `gcs_token`; `gcd` – `gcd_token`; `dropbox` – `dropbox_token`; `acd` – `acd_token`; `hubic` – `hubic_token`; `swift` – `swift_key`; `webdav` and `webdav-http` – `webdav_password`; `fabric` – `fabric_token`; `storj` – `storj_key` and `storj_passphrase`; `smb` – `smb_password`; `one` – `one_token` with the optional `one_client_id` and `one_client_secret`, `odb` – `odb_token` with the optional `odb_client_id` and `odb_client_secret`. `sftp` and `sftpc` take the optional `ssh_password`, `ssh_key_file` and `ssh_passphrase`, a local storage takes no keys. A missing required key is reported at its path, such as `storage.keys.b2_id`, at the key `keys` or `storage`, and a key of another type or `password`, which is `storage.password`, at the key itself. `ssh_key_file`, `gcs_token`, `gcd_token`, `acd_token`, `hubic_token`, `one_token` and `odb_token` hold paths of files: an `env:`, `vault:` or `plain:` reference gives the path, while a `file:` reference gives the content of its file. The values of the keys and the storage itself are not checked, nor is the length of `storage.password`: duplicacy requires a storage password of at least 8 bytes when it creates the storage.
- Every element of `prune.keep` is `n:m` without spaces: keep one snapshot every `n` days for the snapshots older than `m` days, `n` of `0` removes them. Both numbers fit an integer, `m` is at least `1` and strictly decreases along the list, while `n` is not ordered; an element gets at most one problem. The format is always checked, a non-empty `prune.keep` is required when `prune.enabled` is set; `prune.threads` is at least `1`. The command `prune` requires a non-empty `prune.keep` also when `prune.enabled` is not set: without it `prune`, `--dry-run` included, logs `level=ERROR msg="invalid configuration"` with the fields `file`, `line` and `column` of the value or of the nearest present key, `path=prune.keep` and `error="required by the command prune"` before the secrets are resolved and exits with `2`. `prune.exclusive: true` gives the warning `exclusive prune removes the chunks at once, it is safe only when nothing else uses the storage`: an exclusive prune deletes the unreferenced chunks at once instead of keeping them as fossils, so it must run only while no backup of another instance or computer writes to the storage.
- `check.every` is not negative and is above zero when `check.enabled` is set; `check.test_restore_bytes` is not negative, `0` is allowed.
- An empty or missing `targets` gives the warning `no targets configured`. Every target has a `name` that matches `^[A-Za-z0-9_][A-Za-z0-9_.-]*$`, so `.`, `..` and a name starting with `.` or `-` fail, unique among the targets, and a `transport` of `local` or `ssh`. A target without sources gives the warning `target "<name>" has no sources`.
- An `ssh` target requires `host`, `user` and `known_hosts`, an absolute path; `port` is from `1` to `65535`, `connect_timeout` is above zero and `auth` is a non-empty list of `agent`, `key` and `password` without repeats. `key` is required when `auth` has `key` and `password` when it has `password`; a `key` or a `password` without its method is allowed, a non-empty `key_passphrase` requires `key` in `auth`.
- A `local` target has none of `host`, `user`, `port`, `auth`, `key`, `key_passphrase`, `password`, `known_hosts` and `connect_timeout`, also through `<<`; every such field is reported at its key, an explicit `null` is allowed and `''` is not.
- Every source has an `id` that matches the pattern of `name` and is unique inside its target; the problems of the source type are reported too. A repeated `name` or `id` is reported at the key of every repeat after the first, an empty one only as `required`.
- Every secret reference has the syntax of its prefix below, except the fields that a local target does not allow, a `vault:` reference in `vault.token` and the keys of `storage.keys` rejected as keys of another type or `password`; a broken reference is reported without its value.

### Secrets

A secret field – `vault.token`, `storage.password`, the values of `storage.keys`, `targets[].key`, `targets[].key_passphrase`, `targets[].password` and the secret fields of the sources – holds a reference:

- `plain:<value>` – the value itself;
- `env:<NAME>` – the environment variable `NAME`;
- `file:<absolute path>` – the content of the file without the surrounding whitespace;
- `vault:<mount>/<path>/<key>` – the key of a secret of the Vault KV version 2 engine at `vault.address`;
- a string without a prefix is taken as `plain:` with the warning `value without prefix is treated as plain`, so a typo in a prefix, such as `evn:X`, gives a plain value with this warning.

The commands `init`, `backup`, `prune`, `check`, `verify` and `list`, also with `--dry-run`, resolve every reference after the validation and before anything else; `config validate --resolve` does the same after the validation, while `config validate` without the flag and `config show` do not resolve. The reference in `vault.token` is not resolved with them: the Vault client resolves it at the first `vault:` reference, so without `vault:` references `vault.token` is not read and Vault gets no request. The references are resolved one by one in a fixed order of the fields of the configuration, which does not depend on the order of the sections in the file, a value is read once per run and is never written to the log or the output, while a failure is not remembered, so a later request of the same reference reads its source again; the Vault client below has two exceptions:

- `plain:` and a string without a prefix give the value as it is;
- `env:` gives the value of the variable as it is, the surrounding whitespace included; a variable that is not set or is empty is an error;
- `file:` gives the content of a regular file or of a link to one, such as a file in `/run/secrets`, without a leading UTF-8 byte order mark and the surrounding whitespace, a trailing CR included; a directory, a device, a named pipe, a socket, a file larger than 65536 bytes and a file that is empty after the trimming are errors;
- `vault:` reads the key from the Vault KV version 2 engine at `vault.address` with the token of `vault.token`: an `env:`, `file:` or `plain:` reference or a string without a prefix. An empty token and a token with a byte other than the printable ASCII characters from `0x21` to `0x7e` are errors that name neither the token nor its byte; as `env:` keeps the value as it is, a trailing newline or a space in the variable is an error too, while `file:` trims the surrounding whitespace. One client serves the run and makes its requests one at a time; `vault.timeout`, `30s` by default, limits one attempt of a request as a whole: the connection, TLS, the response headers and the body. A missing secret, a missing key, an empty or non-string value, a response body larger than 1 MiB (1048576 bytes), a failed connection and a response other than `2xx`, such as `vault returned 403`, are errors; redirects are not followed, so a `3xx` response is the error `vault returned <code>` too. The errors name the path of the secret but never the URL, the token or the body of the response; the error of a failed connection may name the host and the port. A failed connection, a timeout of an attempt and a `429` or `5xx` response are retried on the schedule of `global.retry`: its `max_retries_time` limits the wait between the attempts of one request, the time of the attempts is not counted, and the header `Retry-After` is ignored. The other errors are not retried: `403`, `404`, a `3xx` response and any other response outside `2xx` except `429` and `5xx`, a failed verification of the certificate, an `https://` address on a port that serves plain HTTP and a response body larger than 1 MiB, the error `vault response is too large`. Every failed attempt that is retried, the last one included, is logged as `level=WARN msg="vault request failed"` with the fields `operation`, such as `vault read depot/mega-doub/prod` for `vault:depot/mega-doub/prod/<key>`, `attempt`, the number of the attempt from 1, and `error`, which names neither the URL nor the token. A request that runs out of the retries on a failed connection, a timeout, `429` or `5xx`, also when the retries are disabled, is remembered for the run: Vault counts as unavailable, and the other `vault:` references get the same error at once without a request, so the budget is spent once per run. A cancellation of the run during a request or the wait between the attempts stops it with the exit code `4` and is not remembered. The proxy and the trusted certificates come from the environment: `HTTP_PROXY` for an `http://` address, `HTTPS_PROXY`, `NO_PROXY` and their lower-case forms, `SSL_CERT_FILE` and `SSL_CERT_DIR`; requests to loopback addresses bypass the proxy. For an `https` address the client uses TLS 1.2 at least and never turns the verification of TLS off, and `vault.ca_file` adds the certificates of its file to these trusted certificates; with an `http` address the client neither reads nor uses `vault.ca_file` at run time. `config validate` without `--resolve` checks only that the path of `vault.ca_file` is absolute, whatever the scheme of the address. For an `https` address the file is read when the client is created at the first `vault:` reference, after the token has resolved, so with an unresolved token the file is not read and its errors show only after the token is fixed, and it is parsed with Go `encoding/pem` and `crypto/x509`: it is a regular file of at most 1 MiB (1048576 bytes) with a leading UTF-8 byte order mark dropped, every PEM block that `encoding/pem` decodes is a `CERTIFICATE` without headers that parses, at least one block is there and only whitespace follows the last decoded block. Anything else is an error: a missing file, a file that is not regular or is larger than 1 MiB, a file without certificates, another type of a block, a block with headers, a certificate that does not parse and other data after the last block. The error of a block names its number, counted from 1 over the blocks that `encoding/pem` decoded only; for a block of another type it quotes the first 64 characters of the type with the escapes of Go `%q`, so an ASCII control byte takes four characters and another escaped character up to ten, and for a certificate that does not parse it adds the error of `crypto/x509`, which may quote a field of the certificate, such as a name or a URI. Apart from the type and the error of `crypto/x509`, no error quotes the content of the file, the base64 body of a block included. `encoding/pem` skips without an error everything it does not decode as a block, and the certificates of such a block are not added to the trusted ones: text before and between the blocks, a block with broken base64, a block with other text on its `-----BEGIN` or `-----END` line, as when two files are joined and the first does not end with a newline, a `-----BEGIN` line with a tab instead of the space, and lines separated by a byte other than `\n`, such as `\r` alone; a leading byte order mark is dropped only at the start of the file. An error comes only when no decoded block follows the skipped content: `no certificates found` or `trailing data after block N`. A certificate that did not get into the pool shows up as a TLS verification error when connecting to Vault only if the Vault server requires that certificate. The client is created once per run, and a failure to create it – the token does not resolve, `vault.ca_file` is broken or the system certificates fail to load – is remembered for the run: the other `vault:` references get the same error without a new attempt, an exception from the rule that a failure is not remembered, like the unavailable Vault above.

Every reference that fails is logged at once as a separate record `level=ERROR msg="secret resolution failed"` with the fields `path`, `kind` (`plain`, `env`, `file` or `vault`), `file` (absolute path), `line` and `column` of the value and `error`, which names the variable or the path but never the value, ordered by position, and the exit code is `2` with nothing in stdout. A failure of the token of Vault is logged once as a record with `path=vault.token`, the `kind` of the reference of the token, the position of its value and the full error, and every `vault:` reference that it fails gets a record with the short error `vault token is unresolved`; a failure of `vault.ca_file` or of the system certificates is logged with its full error at every `vault:` reference. When every reference resolves, `level=INFO msg="secrets resolved"` is logged with the number of the references in the field `count`. A boolean flag with a value is written as `--resolve=false` or `--dry-run=false`: `--resolve false` gives an extra argument and the exit code `2`.

## Storage

`mega-doub init` initializes the storage of `storage.url` as `duplicacy init` does without flags: a storage without a config gets a config encrypted with `storage.password` with the default chunk sizes of duplicacy and the subdirectories `chunks` and `snapshots`, and the run logs `level=INFO msg="storage initialized"`; a storage that has a config is only opened with the password and stays as it is, and the run logs `level=INFO msg="storage already initialized"`, so a repeated `init` changes nothing. Both records have the fields `instance` and `storage`, the URL of the storage without the password of its user information, and the exit code is `0`. duplicacy requires a storage password of at least 8 bytes when it creates the config. Without `--dry-run`, `init` logs `level=INFO msg="secrets resolved"` and `level=INFO msg=command` as the stubs do, prints nothing to stdout, takes the run lock, see [Output](#output), and opens the storage with `storage.threads` threads; it does not create or change `global.copy_dir`, while `global.state_dir` gets the file `lock` and the subdirectory `duplicacy` with the settings of duplicacy. With `--dry-run` it behaves as the stubs with `--dry-run` and touches neither the lock, nor `global.state_dir`, nor the storage.

Every attempt of `init`, `backup` and `prune` to open the storage that fails with a transient error, such as a refused connection, is logged as `level=WARN msg="storage request failed"` with the fields `operation`, `storage init <storage.name>` for all three commands, `attempt` and `error` and is retried on the schedule of `global.retry`. A failure of the opening – a wrong password, a config that cannot be read, a permanent error of the storage or the retries running out – is logged as `level=ERROR msg="storage operation failed"` with the fields `operation`, `init` for `init` and `open` for `backup` and `prune`, `id`, the log ID of duplicacy when the error comes from duplicacy, and `error`, the full error with its cause and the values of the secrets replaced with `***`, and the exit code is `3`. A signal or `global.timeout` during the opening stops the wait between the attempts at once, but an attempt that is already running is not interrupted: the run waits for it to return and holds the run lock meanwhile, then exits with `4` and the record `interrupted` or `timed out` instead of `storage operation failed`, so a storage that has accepted the connection and does not answer may delay the exit.

The limits of `duplicacy init` stay: the first initialization of a shared storage must be made once and from one host, and a backend that answers an error with a missing config gets its config overwritten, which makes the old content unreadable: S3 and S3C on the statuses 403 and 404, Azure on an error with 404 in its text, and Storj on any error. A run whose attempt writes the config and then fails with a transient error before the write is confirmed, such as a lost response of the upload or a dropped connection while a subdirectory is created, finds the config at its next attempt, creates the missing subdirectories and logs `storage already initialized`. A run that stops after the config is written and before the subdirectories are created – by a signal, `global.timeout`, the retries running out or a permanent error – leaves the config without them, and a later `init` finds the config and does not create them, as `duplicacy init` does not: they have to be created by hand.

`mega-doub backup` and `mega-doub prune` need an initialized storage: run `init` once, then `backup`. Without `--dry-run` each logs `level=INFO msg="secrets resolved"` and `level=INFO msg=command`, prints nothing to stdout, takes the run lock, see [Output](#output), and opens the storage without initializing it, with the larger of `storage.threads` and, when the run prunes, `prune.threads` threads; `global.state_dir` gets the file `lock` and the subdirectory `duplicacy`, as with `init`, and neither it nor `global.copy_dir` may overlap a local storage, see [Configuration](#configuration). A storage without a config stays without one: the run logs `level=ERROR msg="storage is not initialized"` with the fields `instance`, `storage`, the URL as in the records of `init`, and `hint`, `run 'mega-doub init' first`, and exits with `3`; duplicacy may still create the empty directory of a local storage. With `--dry-run` both behave as the stubs with `--dry-run` and touch neither the lock, nor `global.state_dir`, nor `global.copy_dir`, nor the storage.

`backup` prepares `global.copy_dir` under the run lock before it opens the storage: a missing directory and its missing parents are created with the mode `0700`, an existing one keeps its mode, and in the directory and its subdirectories every entry whose name ends with `.part` in this letter case, an incomplete file of a source, is removed unless it is a directory; the other entries stay. The links inside the directory are not followed: a link with such a name is removed itself and its target stays, and a directory with such a name stays, while `global.copy_dir` itself may be a link to a directory, which duplicacy follows too. The preparation removes files only in the directory that `global.copy_dir` is or links to, never through a link inside it, so a link right in that directory with an absolute target outside it, which duplicacy follows, keeps the `.part` files of its target, and they go into the revision. When anything is removed, the run logs `level=INFO msg="partial files removed"` with the field `count`, also before a failure or a stop of the preparation. Then it backs up the copy directory with `storage.threads` threads and the tag `storage.tag` as a new revision of `storage.snapshot_id` and logs `level=INFO msg="backup completed"` with the fields `instance`, `storage`, `snapshot_id`, `revision`, `files`, `bytes`, `new_chunks`, `new_bytes`, `uploaded_bytes`, `skipped` and `duration`, such as `1.5s`; a copy directory without files is a failure. With `prune.enabled` the backup is followed by a prune. `prune` prunes the revisions of `storage.snapshot_id` by `prune.keep` with `prune.threads` threads and `prune.exclusive` and logs `level=INFO msg="prune completed"` with the fields `instance`, `storage`, `snapshot_id`, `nothing_to_delete`, `deleted`, `fossilized`, `resurrected` and `failed`, the chunks that the prune has changed, and `duration`.

A failure of the preparation or of the backup is logged as `level=ERROR msg="storage operation failed"` with `operation=backup`, a failure of the prune with `operation=prune`, and the exit code is `3`; a failure of the backup or of the prune has the fields `id` and `error` as above, while a failure of the preparation has no field `id` and its `error` is the text of the file system error with the prefix `prepare copy directory:` and a space, in which the values of secrets are not replaced; when the backup succeeds and its prune fails, the record `backup completed` stays. A signal or `global.timeout` stops the preparation before its next entry and a backup or a prune at the next check of duplicacy with the exit code `4` and without `storage operation failed`; a backup or a prune that completes after them logs its record and exits with `4`, and a backup then does not start its prune.

## Output

`mega-doub config show` prints the configuration of the file that the commands use, except the overrides of `global.retry` from the environment, as one YAML document that starts with `---`: the defaults are filled in, the anchors and `<<` are resolved, the `templates` section is left out and a `local` target has no ssh fields. The keys follow the order of the configuration above and the keys of `storage.keys` are sorted, durations are written as `12h0m0s` and sizes as `1536K` or `256M`; a size that looks like a number is quoted, such as `'0'` or `'100'`, and is read back with or without quotes. The commands `check`, `verify` and `list` are stubs for now, and so are `init`, `backup` and `prune` with `--dry-run`: each checks the file the same way, resolves the secrets as described in [Secrets](#secrets), logs `level=INFO msg="secrets resolved"` and then `level=INFO msg=command` with the fields `command`, `config`, `dry_run`, `log_level`, `log_format`, `no_progress`, the effective values of the flags of the command and `enabled` for `prune` and `check`, and prints the same output. With `--dry-run` it then logs `level=INFO msg="dry run, nothing to do"` and exits with `0`, otherwise it logs `level=ERROR msg="command is not implemented yet"` and exits with `3`. `init`, `backup` and `prune` without `--dry-run` log the same records `secrets resolved` and `command` but print nothing, see [Storage](#storage). `mega-doub config validate` prints nothing to stdout and writes no `msg=command` record: it logs the warnings and the problems of the file, with `--resolve` the records of the secrets, and, for a valid file whose secrets resolve when `--resolve` is given, `level=INFO msg="configuration is valid"`. `mega-doub config show` does not resolve the secrets. Every command writes a record only when its level is not below the log level: `warn` leaves out the `INFO` records, `error` leaves out the warnings too. An invalid file and a secret that fails to resolve give no output, a failed write of the output and an output larger than the limit of 1 MiB (1048576 bytes) for a configuration file, which would not load again and is not printed, are logged as `level=ERROR msg="output write failed"` with the field `error` and give the exit code `2`.

The progress bar of `backup` goes to stderr next to the log records but not through the logger: its lines are not records and have no `level`, `msg` or JSON form. On a terminal the bar is redrawn in place, without one, as under systemd or cron, it is printed as lines of text from time to time, so `progress: []` is recommended for a run without a terminal; the log records stay the same. `init`, `prune`, the stubs and every dry run draw no bar; the field `no_progress` of the record `command` is `true` when `--no-progress` or `--no-progress=true` is given or `global.progress` is empty, whatever the value of the flag, and `false` only when `global.progress` is not empty and the flag is absent or `--no-progress=false`.

A run of `init`, `backup` or `prune` without `--dry-run` takes the run lock of its instance: the file `lock` in `global.state_dir`. The directory and its missing parents are created with the mode `0700`, an existing directory keeps its mode, and the file is created with the mode `0600`. The lock is a `flock` on the file held until the run ends, so the system releases it when a run is killed too; the file keeps the process ID of the last holder and a newline and is never removed. While one run holds the lock, another run of the same instance on the same host stops at once: it logs `level=ERROR msg="another run is in progress"` with the fields `lock`, the path of the file, and `pid`, the process ID read from the file, usually of the holder but right after the holder changes possibly of the previous run, or `0` when the file holds no valid number, and exits with `3`. A symbolic link or anything but a regular file in place of the lock file and any other failure to take the lock, such as a missing permission or `global.state_dir` under a regular file, fail the run: it logs `level=ERROR msg="lock failed"` with the fields `lock` and `error` and exits with `3`. The lock is released when the run ends; a failure to release it is logged as `level=WARN msg="lock release failed"` with the same fields and does not change the exit code. The lock does not cover other hosts that share the storage.

The output masks the secrets: a non-empty `plain:` reference and a value without a prefix become `plain:***`, while the `env:`, `file:` and `vault:` references are printed as they are. The output with `plain:***` is not meant to be run as it is: the value of such a secret becomes `***`. A password in the user information of `storage.url` or `vault.address`, an empty one included, is a problem of the validation, so a file with it is never printed. The user information ends before the first `/`, `?` or `#` after `://` and the password follows its first `:`, so these characters in a password must be percent-encoded, such as `%23` for `#`: otherwise the rest of the password is read as the host, the path, the query or the fragment and the password is not found. Secrets in the query or the fragment of a URL are not supported.

## Exit codes

- `0` – success, help, version, a valid configuration for `config validate`, with `--resolve` only when all its secrets resolve, the output of `config show`, a dry run, `init` that has initialized the storage or found it initialized, a completed `backup` with its prune and a completed `prune`;
- `2` – invalid invocation or configuration: no command, unknown command or flag, extra argument, invalid flag value, unreadable or invalid configuration file, an environment variable of `global.retry` that does not parse, `prune` without `prune.keep`, a secret that fails to resolve, a failed write of the output or an output larger than 1048576 bytes;
- `3` – a failure of the storage or of the run lock of `init`, `backup` and `prune`: a failed operation of the storage, such as the preparation of `global.copy_dir` or a copy directory without files, a storage that is not initialized, another run of the instance holding the run lock or a failure to take it; also `check`, `verify` and `list`, which are not implemented yet;
- `4` – interrupted by a signal before or during the command, or stopped by `global.timeout` during `init`, `backup` or `prune`;
- `1`, `5` and `6` are reserved for the failures of the sources, of the protection and of the verification and are not returned yet.
